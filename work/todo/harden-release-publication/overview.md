# Harden OCI packaging and release publication

Today `verify:run` and `release:publish` each invoke `.mise/cluster/push-artifact.sh` (`flux push artifact` without `--reproducible`) independently, and `release:publish` pushes only the OCI artifact without checking whether the version already exists, publishing a GitHub Release with `install.yaml`, or verifying the published result.

**Requirements (from prior lifecycle design work):**

- **Reproducible, tested-equals-published artifact:** identical committed inputs produce byte-for-byte identical OCI digests, and the exact digest verified by `verify:run` is the one published to `ghcr.io/cur8s/<component>:<version>`.
- **Immutability preflight:** refuse to publish if the target version already exists in either channel (OCI tag or GitHub Release) before writing anything. Never merge, retag, or advance versions automatically.
- **Two matching channels:** publish both the OCI artifact (`ghcr.io/cur8s/<component>:<version>`) and the static bootstrap manifest (`artifacts/rendered/deploy/flux.yaml` as `install.yaml` on the GitHub Release) from the exact same generated bytes.
- **Partial-success recovery:** define publication order, idempotent retry, and an explicit recovery procedure when one channel succeeds and the other fails, without retagging.
- **Post-publish verification:** confirm the published OCI digest matches the tested digest, `cur8s.io/*` annotations are present, and the GitHub Release `install.yaml` matches `artifacts/rendered/deploy/flux.yaml`.
- **Laptop and CI parity:** keep the publication flow inside `release:publish` so running it locally or from GitHub Actions later ([finalize-ci-workflows](../../parked/finalize-ci-workflows/overview.md)) runs the same logic.

**Open decisions / experiments to settle when starting:**

1. **Packaging mechanism:**
   - **Option A — On-disk OCI layout in `artifacts/oci/`:** build once locally with a pinned tool (such as `oras`), record its digest, copy the exact layout into the local k3d registry during `verify:run`, and copy the same layout to `ghcr.io/cur8s` during `release:publish`. Requires experimenting against a local k3d registry to confirm Flux `OCIRepository` accepts the produced media types without a `layerSelector` and that repeated builds yield the same digest.
   - **Option B — `flux push artifact --reproducible` from `artifacts/rendered/`:** keep using the already-pinned `flux` CLI, verify empirically that repeated pushes from the same clean commit produce identical manifest digests across `verify:run` and `release:publish`, and drop the reserved `artifacts/oci/` directory.
2. **GitHub Release automation:** whether `release:publish` creates the GitHub Release and uploads `install.yaml` directly (for example via `gh`) or keeps that step separate.
3. **Signing and provenance:** whether cosign signing and provenance attestations belong in 1.0 or a follow-up.
